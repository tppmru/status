# Настройка мониторинга

## Включение мониторинга

1. Создайте GitHub App в организации `tppmru` и установите его только на `tppmru/status`. Дайте ему права чтения и записи `Contents` и `Issues`. В переменную GitHub Actions `GH_APP_ID` запишите **Client ID**, а в секрет `GH_APP_PRIVATE_KEY` — закрытый ключ приложения. [Настройки переменных и секретов GitHub Actions](https://github.com/tppmru/status/settings/secrets/actions)
2. В ServiceDesk подготовьте служебную заявку с темой `TPPM-STATUS-PROBE` без пользовательских данных. Создайте отдельную учётную запись с минимальными правами чтения этой заявки. Добавьте полный HTTPS URL заявки без параметров в секрет `SDP_PROBE_URL` и выделенный ключ чтения в секрет `SDP_PROBE_TOKEN`.
3. В **Actions → Статус сервисов** запустите workflow с основной ветки. Публичная проверка Frontend и Backend запускается независимо от готовности секретов. Журнал показывает HTTP-статус и результат проверки маркеров.
4. В **Settings → Pages** выберите **Deploy from a branch**, ветку `gh-pages` и папку `/(root)`. Проверьте первую публикацию на странице и дождитесь следующего запуска по расписанию. [Настройки GitHub Pages](https://github.com/tppmru/status/settings/pages)

Исходная ветка хранит конфигурацию и результаты измерений. Ветка `gh-pages` содержит опубликованный сайт. Пока GitHub App и ServiceDesk не настроены, workflow оставляет опубликованную страницу в режиме ожидания.

## Контракты проверок

- **Frontend**. Стартовая страница отвечает HTTP 200 и содержит заголовок «Технополис бот поддержки» и контейнер приложения. Эта проверка охватывает выдачу HTML.
- **Backend**. Ожидается OpenAPI JSON с маршрутом `/api/statuses` и HTTP 200. Если рабочий прокси закрывает документацию, замените проверку после развёртывания отдельного `/api/healthz`.
- **ServiceDesk On-Premise**. Запрос служебной заявки должен ответить HTTP 200, вернуть код `2000` внутри `response_status` и ожидаемую тему. Upptime отправляет ключ в заголовке `authtoken`, проверяет TLS и не следует редиректам.

Плановые проверки запускаются каждые пять минут. История времени ответа, графики и статические страницы пересобираются ежедневно и при ручном запуске. GitHub Actions может задерживать запуск по расписанию. Короткие закрытые инциденты сохраняются.

Чтобы проверить восстановление без остановки рабочих сервисов, используйте отдельный тестовый репозиторий и управляемые HTTPS-заглушки с теми же маркерами. Поочерёдно возвращайте ошибочный ответ для одной из трёх проверок, затем восстанавливайте штатный ответ. Проверьте открытие и закрытие инцидента и историю статусов.
